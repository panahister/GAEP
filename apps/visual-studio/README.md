# GAEP for Visual Studio

The Visual Studio host uses Microsoft's out-of-process `VisualStudio.Extensibility` model and communicates with the same `gaep-engine` stdio protocol used by Rider. `Gaep.VisualStudio` contributes a native Tools-menu command and Remote UI Product Studio tool window; `Gaep.HostClient` is the IDE-independent bounded protocol client packaged beside it.

`npm run test:visual-studio:host` compiles the native shell and generated contribution manifest, verifies that both extension services are out of process, checks the Product-workflow Remote UI bindings, and runs the dependency-free protocol and controller checks. On Windows, the same build also creates and verifies `Gaep.VisualStudio.vsix`. On other systems, final container creation and installation remain explicitly unverified because Microsoft's `VsixUtil.exe` requires Windows.

The development client resolves `GAEP_ENGINE_EXECUTABLE` to a canonical absolute file, captures its SHA-256 before first launch, revalidates it before every restart and immediately after process start, serializes requests, drains stderr, and bounds response frames. `GAEP_ENGINE_SHA256` can provide the expected 64-character digest (with an optional `sha256:` prefix) and makes a mismatch fail closed. Capturing a locally selected digest detects replacement; it is not a publisher-authenticity claim.

The Remote UI accepts one absolute local workspace folder (or starts from `GAEP_WORKSPACE_PATH`), reads the exact Product identity and revision, shows Codex/Claude readiness, loads guarded adapter/model/non-sensitive portable-setting choices, lists and reads governed portable-design metadata, and imports one local folder after a cancel-default confirmation. Agent Selection is loaded separately, invalidated when the workspace changes, and recorded only after a second cancel-default prompt. The shared engine rejects active Runs, capability drift, legacy or invalid state, and post-Run changes that require a versioned handoff. Selection does not start a provider, create or resume a Run, approve tools or effects, or grant execution authority. Executable paths, provider credentials, sensitive settings, and raw engine output are withheld.

Versioned Agent Handoff is a separate cancel-default workflow. It binds the latest terminal Run, current Product and Initiative, exact current Agent Selection, and verified capability snapshot before the user can choose a changed adapter, model, or portable setting. It accepts a bounded portable reason plus comma-separated completed-work, unresolved-matter, decision, and evidence entries. Immediately before mutation, the engine revalidates the Run and selection; the returned receipt must echo the expected source binding, target identity, portable settings, and history exactly. A successful handoff atomically replaces portable Agent Selection but still cannot start or resume a provider, create a Run, approve tools or effects, or grant execution authority. Absolute paths, encoded path traversal, credentials, sessions, executable details, and undeclared response fields fail closed.

The Managed Run evidence surface is a separate audit-gated observation path. It reads pages of at most 100 summaries from the engine's 2,000-record, 200-row maximum snapshot-stable inventory, reports the exact offset, total and page omission count, and binds every next-page request to the first page's snapshot digest and total. Previous navigation uses only already verified pages. The HostClient rejects stale snapshots, total/count/offset drift, non-progressing pages, undeclared/private fields, result/evidence identity or digest rebinding, inconsistent terminal truth, invalid count maps, and mismatched apply-decision receipts. Rendered output contains only portable identifiers, states, counts, digests, warning codes, and timestamps; prompts, provider output, changed paths, source bytes, executable/process/workspace data, and credentials are withheld. The surface cannot start, resume, cancel, apply, discard, approve, or grant Tool, write, effect, outcome, implementation-readiness, release, or future Run authority.

Exact staged review is a separate mutation-capable workflow for one pending `codex-staged` Managed Run. The HostClient verifies one positive Run revision, canonical preview digest, result/evidence binding, complete ordinally sorted changed-file inventory of at most 512 entries with zero omissions, exact before/after digest-size-mode triples, excluded-path digest, and a host-owned write envelope of at most 256 scopes. Loading and rendering a review is read-only. Apply and discard are separate commands; each requires two cancel-default Remote UI prompts bound to the displayed Run ID, revision, preview digest, inventory digest, and—when applying—write envelope. The client sends no caller-selected paths. It rejects stale, rebound, private-path, undeclared-field, incomplete-metadata, non-canonical-digest, and invalid-transition responses. Apply records post-apply Workflow gates as `not-assessed`, so provider completion cannot become governed outcome satisfaction. Apply/discard receipts prove verified persisted state only; machine-local stage and recovery-journal cleanup remain separate claims.

Import reads the Product binding twice and stops if its identity or revision changes. Rendered results contain validated metadata and digests rather than bundle paths or source content, and every import remains pending human review.

Release packaging will bundle signed Windows engine binaries and supply their approved digest. It will not invoke a mutable executable found later on `PATH` without identity binding and digest verification. Native Windows installation, Visual Studio activation, solution-path auto-selection, rendered Remote UI interaction, and interactive staged-review confirmation acceptance still require a Windows verification run; this non-Windows checkpoint does not claim them.
