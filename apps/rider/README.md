# GAEP for Rider

This host is a thin Rider tool-window client for the shared `gaep-engine` stdio protocol. It deliberately contains no duplicate Product, governance, adapter, or authorization logic.

The native Product tool window reads the exact Product binding, exposes Codex/Claude readiness, guarded-selection, versioned-handoff, managed read-only execution, Managed Run evidence, and exact staged-review flows, and provides bounded portable-design metadata list/read/import actions. Readiness conservatively projects verified adapter, runtime, model, and capability metadata. Selection can record one detected adapter, verified or engine-revalidated model ID, and non-sensitive portable settings after explicit confirmation. It fails closed for active Runs, capability drift, legacy or invalid state, and post-Run changes that require a versioned handoff. Handoff binds the exact current selection and latest terminal Run to a freshly observed changed target, requires bounded portable history plus cancel-default confirmation, rechecks state before submission, and atomically records the handoff and target selection. Selection and handoff do not start or resume a provider, create a Run, approve tools or effects, or grant execution authority. Executable paths, provider credentials, sensitive settings, and raw engine output are withheld.

The `Show phase dashboards` action requests the shared Phase 0/1A dashboard projection for the exact current Product ID, revision, and canonical Product digest. Rider strictly verifies the delivery-phase catalog, three canonical panel contracts, governed applicability decisions, portable text bounds, response binding, and composition digest before rendering only bounded metadata. Extra or private fields, stale Product bindings, forged applicability, catalog drift, and digest drift fail closed. The dashboard remains a read-only projection: it cannot decide phase applicability, approve a phase, establish readiness, or grant implementation or release authority.

The `Show Change and impact…` action first loads an audit-gated, digest-bound catalog of exact current Change references for the exact Product revision. After the human selects one reference, Rider requests and independently verifies that exact Change revision and digest, bounded Work Item/artifact/effect/trace rows, Decision and Risk bindings, freshness counters, category limits, omission state, authority boundaries, portable locators, and the complete snapshot digest. The rendered view contains metadata only: Product, Change, and Work Item text, source bytes, absolute paths, prompts, provider output, executable state, and credentials are withheld. Selection is not Change approval; the projection cannot accept Risk, mutate records, start a Run, invoke a Tool, or authorize an effect.

The `Show Agent and model` action performs fresh capability and Agent Selection reads before requesting the shared exact Agent/Model projection. Rider binds the request and response to the current Product revision and digest, every observed adapter/agent capability digest, and the exact selected, unselected, migration-required, or invalid selection state. It independently verifies bounded capability, Run, handoff, Managed Run result/evidence, freshness, omission, and limitation metadata plus the canonical snapshot digest. Provider usage and cost remain explicitly unavailable because current Managed Run records carry no such contract. Sensitive settings are rendered only through the shared redacted projection. Extra/private fields, stale or rebound selections, capability drift, forged counts or freshness, invented metrics, and digest drift fail closed. This observation-only view cannot select or switch an agent, create a handoff, launch a Run, authorize a Tool/write/effect, approve an outcome, establish provider-account or native-host readiness, or grant release authority.

The separate `Browse accessible dashboard tables…` action preserves those immediate read-only dashboard actions and adds a native keyboard and screen-reader flow across the same strict Phase, Change/Impact and Agent/Model responses. The user selects one verified table, keeps source order or deterministically sorts one visible column, and enters an optional case-insensitive visible-metadata filter of at most 256 characters. Rider renders a named plaintext alternative with exact visible, bounded, omitted and source totals plus snapshot, source and authority boundaries. A separate cancel-default confirmation copies only the current visible columns and filtered rows as formula-neutralized CSV through the IDE clipboard; it writes no file, includes no hidden field or omitted record, and grants no state, approval, Run, Tool, write, effect, readiness, release or acceptance authority.

Managed read-only execution renders and independently verifies an exact Charter/Workflow preview before a separate cancel-default attestation, fixes the timeout at 120 seconds, denies every Tool, write and non-observation effect, and renders the terminal provider disposition separately from the governed outcome. The Managed Run evidence actions are observation-only and audit-gated: the browser shows pages of at most 100 records with exact total and omission counts, binds every later page to the first page's snapshot digest and total, and keeps prior verified pages for exact back navigation. Changed totals, snapshots, offsets, counts or non-progressing pages fail closed; exact read verifies one result/evidence projection by UUID and digest. Only portable IDs, states, counts, digests, warning codes and timestamps are displayed. Prompts, provider output, source bytes, changed paths, executable paths, process state, workspace paths and credentials are omitted. The view cannot start, resume, cancel, apply, discard, approve, or grant outcome, implementation-readiness, release, Tool, write, effect, or future Run authority.

Exact staged review is a separate mutation-capable workflow for one pending `codex-staged` Managed Run. Rider verifies one positive Run revision, canonical preview digest, result/evidence binding, complete sorted changed-file inventory of at most 512 entries with zero omissions, exact before/after digest-size-mode triples, excluded-path digest, and a host-owned write envelope of at most 256 scopes. Opening the review is read-only. Apply or discard requires a first cancel-default decision and a second cancel-default confirmation bound to the displayed Run ID, revision, preview digest, inventory digest, and—when applying—write envelope. The client sends no caller-selected paths. It rejects stale, rebound, private-path, extra-field, incomplete-metadata, non-canonical-digest, and invalid-transition responses. Apply records post-apply Workflow gates as `not-assessed`, so provider completion cannot be promoted to governed outcome satisfaction. Apply/discard receipts prove verified persisted state only; machine-local stage and recovery-journal cleanup remain separate claims.

Import selects one existing local folder, rechecks Product identity and revision before the request, retains only engine-validated metadata and digests, and always reports the result as pending human review. Files, archives, `.fig` ingestion, remote URLs, OAuth, live design-tool accounts, raw source content, local paths, credentials, and upstream approval escalation are outside this surface.

The plugin archive now contains `engine/gaep-engine.mjs`, a deterministic bundle of the shared engine host, beside the plugin JAR. Its build-time SHA-256 is compiled into the plugin. In package-local mode Rider requires `GAEP_ENGINE_RUNTIME_EXECUTABLE` to name one absolute Node-compatible runtime; mutable `PATH` fallback is disabled. `GAEP_ENGINE_RUNTIME_SHA256` may optionally pin that runtime. The client resolves both runtime and module to canonical regular files, captures or verifies their SHA-256 identities before every start, and rechecks both immediately after process launch. Provider credentials and other inherited environment authority are stripped; only bounded locale, temporary-directory, platform-launch and `PATH` values are retained.

An operator may instead set `GAEP_ENGINE_EXECUTABLE` to an explicit external engine and optionally pin it with `GAEP_ENGINE_SHA256`; that override preserves the earlier external-engine development boundary. Requests are serialized and JSON-validated, stderr is drained, response frames are bounded, and process-tree termination is attempted on failure or disposal. Local digest binding detects replacement but is not publisher provenance, signing, notarization, or supported-platform certification.

Release packaging will bundle signed platform-specific engine binaries and supply their approved digests before launch.

Build requirements follow the official IntelliJ Platform Gradle Plugin 2.x baseline: Gradle 9 or newer and Java 17 or newer. The configured toolchain is Java 21.

From the repository root, `npm run test:rider:package` performs a clean test, mandatory IntelliJ bytecode instrumentation, plugin assembly, archive-structure verification, and exact byte parity for both the packaged JAR and package-local engine across the generated bundle, archive, and isolated Rider 2025.3 prepared sandbox. The strict client test launches the real generated engine through an explicit absolute runtime, requires the exact empty audit-gated Managed Run evidence page, proves no `.gaep` mutation, and rejects a mismatched module digest. The gate also revalidates the sandbox descriptor's exact ID, version, native activation listener and GAEP tool-window factory. Finally, a bounded helper compiles against the exact cached Rider 2025.3 build and invokes JetBrains' own `PluginInstaller.rootEntryName` and `PluginInstaller.unpackPlugin` APIs on the built ZIP inside a fresh temporary plugin directory. It verifies the installed package-local engine and JAR byte-for-byte against the prepared sandbox, explicitly removes the temporary installation, proves absence, reinstalls through the same API and requires exact byte parity. The installable output is `apps/rider/build/distributions/gaep-rider-0.1.0.zip`, with stable plugin ID `dev.gaep.productstudio`. This local package gate proves exact archive unpack/install semantics and one client-level read-only workflow; it is not Plugins UI/Marketplace installation, IDE-managed uninstall, signing/provenance, rendered tool-window interaction, real-provider execution, supported-platform certification or Product Owner acceptance.

`npm run test:rider:startup` launches the resolved Rider 2025.3 runtime in a bounded process group, waits up to 90 seconds for fresh log evidence that exact plugin `dev.gaep.productstudio@0.1.0` loaded with the isolated GAEP config, system, plugin, and log paths, and requires the packaged plugin's native application-initialization code to emit the exact no-provider/no-write-authority activation marker before terminating the sandbox process tree. It proves native runtime startup, plugin loading, and execution of packaged plugin code on the executing host. It does not automate the tool-window UI, prove that the native Rider UI invoked the packaged engine, test plugin-manager installation, interactively accept the staged-review confirmations, or grant host acceptance.
